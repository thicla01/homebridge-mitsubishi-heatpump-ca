# Changelog

All notable changes to homebridge-mitsubishi-heatpump-ca.

its first stable release; **there is no 2.3.0** — `-ca.N` was a private numbering used

work went out as 2.3.1. Entries from 2.0.0 through 2.2.1 are
inherited from

the project that upstream itself forked from.

- **2.3.2** - A failed local poll says which failure it was (2026-08-23)
  - **Fixed: every local poll failure logged the same sentence, whatever went wrong.** Three episodes on live hardware in three days — 2026-08-20 twice, 2026-08-22 — of 9, 16 and 10 consecutive failed polls, up to four minutes of stale tile each, all reported as `no usable status in the reply`. Nothing in the log could distinguish a unit that was unreachable, one rejecting our credentials, one answering "busy", and one replying without a room temperature — and those call for opposite responses from whoever reads it: check DHCP and wifi, check the credentials, or wait for an overloaded adapter to recover
  - The classification already existed one call down: `requestDetailed` returns a `LocalErrorKind` precisely so discovery can tell "not this device" from "busy right now". `getStatus` discarded it, and the poller logged the resulting `null` with a hardcoded string — the comment at that call site even enumerated the causes it was collapsing. `getStatusDetailed` carries the cause out and `getStatus` stays a facade over it, so the other two call sites are untouched. A new `incomplete` covers the one case the request layer cannot see: a request that succeeded and answered without `roomTemp`
  - `describeLocalFailure` turns each cause into a line written for the person reading `homebridge.log` at the moment their tile went stale — "the unit answered \"busy\" (serializer_error / __no_memory) — it is overloaded or wedged, not unreachable" rather than a state name
  - **This is also the prerequisite for deciding what to do about those episodes.** pykumo escalates a wedged adapter to a rate-limited reboot; whether that is worth adopting here depends entirely on whether these failures are `busy` or `transport`, which was unknowable from the field until now
  - Seven tests, four verified RED by collapsing the causes back to one. One pins the strings themselves — distinct and non-empty per cause — because a `switch` falling through to a shared default would defeat the whole change while every other test still passed. Two existing doubles grew the new method; the second is worth knowing about, since `test/local-sensor.test.ts` stubbed `request` only and so sent the status read to the real network the moment it moved to `requestDetailed`
  - **539 tests total green**
  - Code: `local-api.ts:getStatusDetailed / describeLocalFailure`, `platform.ts:pollLocalStatus`

- **2.3.1** - First stable release: a newly registered unit no longer logs an "illegal value" warning; adapter simulator (2026-08-22)
  - **Fixed: every unit registered for the first time logged `characteristic was supplied illegal value: number 0 exceeded minimum of 10`.** hap-nodejs starts a fresh `HeatingThresholdTemperature` at 0 — its own default range begins there — and the constructor then declares 10-35, so `setProps` re-validated the value it found, complained, and clamped. The clamp made it harmless in effect; the log line does not read that way, and "supplied illegal value" is the sort of thing a user opens an issue about. Both thresholds are now given an in-range value BEFORE the range is narrowed; a unit that already has a usable value keeps it, and the first status read replaces the seed within seconds
  - **Why it hid:** Homebridge persists characteristic values in `cachedAccessories`, so a unit that already exists comes back holding a real setpoint and never trips the validation. Only registration from scratch does — which is what nobody with a single heat pump does twice. It surfaced three times at once the first time three simulated units were run through a real Homebridge. `CoolingThresholdTemperature` happens to default to 10 and never tripped it; it is seeded the same way so the pair cannot drift apart if the declared range moves
  - Three regression tests, mutation-verified RED by removing the seed (2 failures). Two pin OUR value rather than HAP's default — if the plugin always seeds in range, what hap-nodejs starts at stops mattering — and one pins the premise, so a future hap-nodejs default above our minimum turns the seed into dead code someone can delete on purpose rather than a no-op nobody dares touch
  - **Fixed: a setpoint dragged from 26 to 22 visibly bounced** — 22, back to 26, then 22 again. A setpoint command waits `SETPOINT_HOLD_MS` (1.5s) before it is sent, which is what lets an "AC off" dispatched alongside it win; but the guard that keeps a fresh write from being overwritten by an in-flight reading was armed only once the command had SUCCEEDED, leaving the entire hold plus the round trip unprotected. A local poll runs every 15s, so the collision is routine rather than exotic. The guard is now armed when HomeKit asks, and carries the value being written in `setpointPending` — `currentStatus` cannot stand in for it, since during the hold it still holds the OLD setpoint, which is precisely the value that must not win. Released on success (the cache carries it from there), on failure (the device never took it), and when the hold is suppressed
  - **Fixed: a write that changes nothing is no longer sent.** The Homebridge UI's AUTO control is a RANGE slider bound to both handles at once, so moving the cooling handle rewrote `spHeat` too, and it feeds our echo back into its own model — 14 commands for one drag, half of them re-asserting a value that had not moved, still arriving in pairs every two seconds after the user had stopped. Neither cause is fixable from here, but both stop mattering if a no-op sends nothing and echoes nothing (echoing is what re-entered the loop). It is worth more than the count suggests: these adapters hold roughly one connection and the plugin serialises per device, so every redundant write occupies the slot a poll or a real command needs. Two existing tests wrote a value their own fixture already held; their fixtures now start away from it, which restores what each was built to prove rather than relaxing either assertion — both stay green under the mutation that removes the fix
  - **New: `tools/kumo-adapter-sim.mjs`**, a fake LAN adapter, because almost everything local control does with more than one unit had been untestable for a maintainer who owns one heat pump: discovery matching each device to the adapter that authenticates its token, per-unit command routing, `localControlIps` pinning, and the failures — an address nothing answers at, a rejected credential, an out-of-memory adapter, two requests at once — which on real hardware are either impossible or mean breaking a working heating system on purpose. It signs with this repo's own `computeLocalToken`, so it agrees with us by construction and **cannot support a protocol claim**; hardware answers "does the adapter accept this?", the simulator answers "do we do the right thing with N of them?". Not published to npm. See CONTRIBUTING.md
  - Verified on the Homebridge host itself (Linux aarch64 / node 24) as well as macOS / node 22, against the plugin as installed from npm: discovery through shuffled ports and a dead address, command round-trip, sensor humidity, all three fault modes with their correct classifications, and the per-device mutex demonstrated both ways. Then end-to-end through a real Homebridge: three units registered in local-only mode, polled every 15s each, cloud never contacted, zero errors — which is the run that found the bug above
  - **The form now says where a pinned address has to be reachable from** — the machine running Homebridge, which is often not the machine the settings page is open on — with the two commands to confirm a route, since a pinned unit is deliberately never swept for and a wrong address surfaces as "no answer" at the next restart rather than falling back to discovery
  - **First stable release of the fork; the `-ca.N` prereleases end here.** `2.3.0-ca.13` and `2.3.0-ca.14` are on npm — as `latest` and `beta` respectively — and 2.3.1 takes over `latest`, so a plain `npm install homebridge-mitsubishi-heatpump-ca` now resolves to it. There is no 2.3.0: semver reads `2.3.0-ca.15` as a preview of 2.3.0, and publishing a version numbered *below* the ca.14 that had been running in production for days would have read as a step backwards to every human looking at it. The package name keeps its `-ca`; only the version scheme changes. It is a real release rather than a relabel — ca.15 was never published, and two fixes land on top of it
  - **531 tests total green**
  - Code: `accessory.ts` (threshold seeding), `tools/kumo-adapter-sim.mjs`, `config.schema.json`, `docs/configuration.md`

- **2.3.0-ca.14** - `localControlIps` becomes a form field (2026-08-22)
  - **Fixed: the Homebridge UI silently dropped the local IP overrides.** The UI rewrites the platform block from the schema when the settings page is saved or the plugin is reinstalled through it, and an option the schema does not describe as a field is not preserved by that rewrite. `localControlIps` was the one option deliberately left out — a free-form `{ "<serial>": "<ip>" }` map cannot be rendered as fields — with a help block pointing at the JSON editor and a doc claiming any existing value survived. It did not: on 2026-08-21 a reinstall through the UI removed a working pin from a live install, and the startup LAN sweep came back with nothing in the log to say why.
  - The map is now a **list of serial/address pairs**, which the form renders. The layout-coverage test no longer allows an exception: it asserts that *no* schema option is missing from the form, since anything on that list can be dropped.
  - **Both shapes are accepted at runtime** (`normalizeLocalControlIps`): the array the form writes, and the map existing configs and the JSON editor contain. No config change is required. The hazard the helper removes is a quiet one — indexing an array by device serial finds nothing and throws nothing, so a form-written config would have failed exactly like an absent one. Half-filled rows are skipped rather than fatal, being what an in-progress UI edit looks like.
  - Six regression tests across both shapes, mutation-verified. Worth knowing if you repeat it: the obvious mutation (an early return before the array branch) does not compile, and a non-compiling mutation produces the misleading silence `CONTRIBUTING.md` warns about — the one that bites is emptying the loop body.
  - **519 tests total green**
  - Code: `settings.ts:normalizeLocalControlIps`, `platform.ts:resolveV2Units / admitLocalDevices`, `config.schema.json`

- **2.3.0-ca.13** - Renamed `homebridge-mitsubishi-heatpump-ca`, credential-path hardening, SECURITY.md (2026-08-21)
  - **Package renamed to `homebridge-mitsubishi-heatpump-ca`.** Two packages cannot share a name in one Homebridge install, and Homebridge only discovers a plugin whose npm name begins with `homebridge-`, so the fork needs its own name rather than dropping the prefix — "-ca" is the country code already used by `cloudRegion: "ca"`. `repository`, `bugs` and `homepage` now point at [thicla01/homebridge-mitsubishi-heatpump-ca](https://github.com/thicla01/homebridge-mitsubishi-heatpump-ca); the two links that must NOT move are left alone — the upstream attribution in NOTICE and the README fork banner still point at ukaratay's repository, which is the whole point of them. **This fork was not published to npm** when this entry was written; `2.3.0-ca.13` and `2.3.0-ca.14` were pushed there shortly afterwards, and 2.3.1 is the first stable release. And three packages now register the `KumoV3` platform — `homebridge-mitsubishi-comfort`, `homebridge-mitsubishi-heatpump`, and this fork — so 2.0.0's warning generalises: never have any two of them installed together
  - **Security hardening on the credential paths**, out of a five-lens review (secrets, transport, untrusted input, HomeKit surface, availability) that surfaced six items — none a live vulnerability: each needs an attacker already on the LAN or control of the cloud vendor's edge, and none leaks a secret. Four are fixed. **`redirect: 'error'` on all five v3 `fetch` calls** (login, refresh, the shared authenticated-request options inherited by the 401-retry, and `getZones`): a 307/308 would re-send the account password, the refresh token or the bearer header to whatever host `Location` names, cross-origin and https→http — `kumo-v2.ts` already guarded this with the same comment, the v3 module did not, and while only a US/v3 install can reach those calls at all, one codebase ships both. **Address validation at a single choke point** (`setCreds`): the v2 reply's `zone.address` and `config.json`'s `localControlIps` both flow unescaped into `http://<ip>/api?m=<token>`, so a value that is not an IPv4[:port] would aim a signed, real-token PUT at a host the user never named — `isLocalHost()` rejects anything else, and nothing legitimate breaks because the swept addresses are dotted quads. **A 64KB cap on the local HTTP reply**, the request destroyed mid-stream past the cap and surfaced as an ordinary transport failure, so an unauthenticated LAN peer answering an unbounded body cannot grow the accumulator until the poll timer throws. Six regression tests, **each mutation-verified**, including a source check that every v3 fetch carries the redirect guard so a new call site cannot regress it (`test/v3-redirect-guard.test.ts`)
  - **SECURITY.md** states the threat model — what the plugin trusts (the LAN, Homebridge storage, the cloud vendor) and what it defends — so an evaluator does not have to infer it from the code, and documents the two discovery-sweep hardening items deliberately left unfixed, naming `localControlIps` pinning as the robust mitigation for an untrusted LAN
  - **The documentation caught up with the fork.** The verified-by-Homebridge badge is removed rather than restyled — it attests that the UPSTREAM project passed the Homebridge project's verification, which this fork has not, so displaying it claimed an endorsement never given. The inherited `npm install -g homebridge-mitsubishi-heatpump` instruction — which would install upstream's package, the one that cannot serve a Canadian account at all — is replaced by the source and tarball paths. The npm description and keywords say what the fork does instead of advertising the v3 API it never contacts on a Canadian account. NOTICE carries the Apache-2.0 section 4(b) statement of changes for this fork, with the upstream sections preserved intact and renumbered; a real unit's serial in the README, `config.schema.json` and two test fixtures was replaced with a synthetic one of the same shape; and every document was audited against the code — this file's two "Unreleased" blocks becoming the versioned `ca` entries below
  - **512 tests total green**, up from the 465 the series opened with at `ca.5`

- **2.3.0-ca.12** - An isolated credential rejection is retried instead of believed (2026-08-20)
  - The `ca.7` streak assumed a rejected request is one honest piece of evidence about the credentials. It is not quite: **the token signs the BODY, so a request truncated under connection contention surfaces as a signature failure — which the adapter can only call an authentication error.** A rejected request is now retried once after a 250ms pause (`AUTH_RETRY_PAUSE_MS`: long enough for a competing local client to finish its exchange — the adapter holds roughly one connection — and invisible next to a 15s poll). The retry is safe because every command the plugin sends is an idempotent absolute-value write, never a delta
  - **The streak counts REQUESTS, not attempts.** A retried request that fails twice is still one piece of evidence, not two — counting attempts would cross the `ca.7` threshold in two polls instead of three and undo its point. A genuinely wrong credential pays the pause once per poll and still crosses the threshold inside a minute of startup; the isolated rejection observed live costs the caller nothing at all — the second attempt succeeds, so no error, no warning, no gap in the poll history
  - One prior test is **deliberately inverted**: it used to assert a rejection is NOT retried, on the reasoning that a well-formed rejection "will say the same thing again". The hardware disagreed on 2026-08-19 — one poll in ~30 rejected and the next fine, twice in a day, with credentials that are provably correct, since `computeLocalToken` is a pure function of the password, cryptoSerial and body — and the test now asserts the opposite by name (`device_authentication_error classifies as auth and IS retried once`). The warning also names its unit of counting ("N requests in a row"): the poller prints its OWN failed-poll counter on the neighbouring line, and live on 2026-08-20 the two landed one line apart reading "(2 in a row)" and "3 times in a row" — which reads like a contradiction until each counter says what it measures
  - Code: `local-api.ts:AUTH_RETRY_PAUSE_MS / noteRequestOutcome`; tests in `test/local-http.test.ts` (retried once; an isolated rejection costs nothing; the streak counts requests, asserted against the attempt count)

- **2.3.0-ca.11** - An "AC off" scene can no longer revive the unit through the Fanv2 tile (2026-08-20)
  - Fixed: this accessory publishes a Fanv2 tile alongside the climate tile, and a scene recorded while the unit was running stores that tile as ACTIVE and re-pushes it on every trigger. The tile delegates an ON to `setActive`, whose `noteModeIntent()` zeroes the off-suppression window — so it did not merely evade the 1.7.2 guard, it DISARMED it for the setpoints dispatched behind it, and a bare mode-less setpoint revives a unit over the LAN. Observed live 2026-08-20: a scene whose only purpose was to stop the heat pump left it running in auto, with both AUTO setpoints accepted a second later
  - Fix: a fan-tile ON is refused while an off is in flight — and only then, so "turn on the fan" on an idle unit still turns it on, which is the whole point of delegating an ON there. The regression test deliberately models transport latency AND the per-device mutex: with an instant fake transport the off's optimistic `power = 0` lands first and the bug hides
  - Regression: `test/off-guard-mode.test.ts` (the fan-tile cases: a tile ON does not let the scene setpoints trail the off, no active mode follows the off either, and an ON with no off in flight still turns the unit on), verified to fail against the build that preceded it
  - Code: `accessory.ts:setFanActive`

- **2.3.0-ca.10** - A superseded reconcile no longer bounces the setpoint (2026-08-20)
  - Fixed: two ordinary setpoint taps two seconds apart — 22 → 22.5 → 23, observed live 2026-08-20 — scheduled two post-write reconciles, and the FIRST read the adapter before it had applied the second write. It found 22.5, published it over the 23 already on the tile, and the second reconcile then put 23 back: a visible bounce on the value the user had just set, plus two contradictory log lines blaming the device for holding a value nobody had asked it to keep any more
  - Fix: the write path already tracked ownership per field (`setpointWriteGen`, via `holdSetpointWrite`); the reconcile simply was not consulting it. `scheduleSetpointReconcile` now records the generation when it is scheduled and bails if a newer write owns the field — that write's own reconcile is the authority. The generation is bumped at the START of a write, so a write still inside its hold already supersedes an older reconcile
  - Regression: `test/setpoint-reconcile-bounce.test.ts`, verified to fail against the build that preceded it
  - Code: `accessory.ts:scheduleSetpointReconcile`

- **2.3.0-ca.9** - An "AC on" scene's setpoints are no longer silently lost (2026-08-20)
  - Fixed: HomeKit dispatches every characteristic of one write request concurrently, and `setActive` marks the unit on only AFTER its command resolves — so every setpoint in an "AC on at 22" scene burst read `power === 0`, was cached and echoed to HomeKit, and never reached the adapter. The unit then ran at its old setpoint while the Home app showed the new one; no error, no revert — the command was simply lost. The exact mirror of the 1.7.2 off-scene race, on the opposite edge
  - Fix: the synchronous entry guard in `setThresholdTemperature` is now `offInFlight()` — only an off actually in flight suppresses immediately. The merely-off case is deliberately NOT decided there: it is decided after the 1500ms hold, by the same predicate, which reaches the same verdict 1.5s later — by which time a concurrent scene ON has resolved and flipped the cache. Every protection holds: a genuinely idle unit is still suppressed post-hold, so a bare setpoint still cannot revive it, and if the concurrent on command FAILS the cache stays `power: 0` and the setpoint is suppressed too
  - Regression: `test/on-scene-setpoint-lost.test.ts`, verified to fail against the build that preceded it
  - Code: `accessory.ts:setThresholdTemperature / holdSetpointWrite`

- **2.3.0-ca.8** - Saving the Homebridge settings form can no longer idle a working install (2026-08-19)
  - Fixed: the `ca.5` validator was written on the assumption that a value present in `config.json` is one the user chose — "only an EXPLICIT value contradicts". The Homebridge UI breaks that assumption: saving the settings form materialises every schema `default` into `config.json`, so an untouched field arrives looking exactly like a deliberate choice. **Merely opening the settings page of a working Canadian install and pressing Save wrote `localCredentialSource: "v3"` into it, and the platform went idle on the next restart** — observed on real hardware, 2026-08-19. No amount of care in the schema fully fixes that, because the UI is free to write whatever it likes; the runtime has to be able to absorb it
  - New `reconcileImpliedConfig()` runs BEFORE `validatePlatformConfig` and absorbs a contradiction that has exactly ONE possible resolution: the value is deleted, and a warning names what was ignored, that the UI writes it on its own, and the config-editor deletion that silences it. Three of the six `ca.5` rejections are absorbed this way — `ca` + an explicit `v3` source, and `localControl: false` under either v2 route — because under `cloudRegion: "ca"` the v2 source and LAN control are not preferences, they are the only things that exist (v3 answers those accounts HTTP 500 and there is no other transport), so refusing to start buys no safety and costs the user their heat pump. Genuinely ambiguous contradictions stay fatal in the validator, where failing loudly IS the safe answer: a misspelled enum, `localOnly` + a v2 source, missing credentials. The absorption cannot tell an explicit value from a UI-manufactured one — that is both the point and the price
  - **Schema defaults removed from fields whose ABSENCE is meaningful**, so the UI cannot manufacture them again: `localCredentialSource`, and the ten `localDevices` capability flags that were materialising a phantom device with no serial
  - `test/credential-source-warnings.test.ts` now pins the absorption where it used to pin the rejection: taking the "set `localControl: false`" advice gets the value deleted with a "was ignored" warning and a config that stays valid — either way the advice silences nothing, which is why it is never given under a v2 source
  - Code: `platform.ts:reconcileImpliedConfig`, `config.schema.json`

- **2.3.0-ca.7** - The credentials-rejected warning waits for three rejections in a row (2026-08-19)
  - `device_authentication_error` — the adapter answering HTTP 200 to say it rejected the token — was treated as the one error that is certainly a config fault, and warned about on first sight. The hardware disagreed on 2026-08-19: one poll in ~30 was rejected and the next succeeded, twice in a day, with credentials that are provably correct — `computeLocalToken` is a pure function of the password, cryptoSerial and body, so a wrong credential cannot fail intermittently. Warning on a single rejection sent the user hunting a configuration fault that did not exist (`ca.12` below found the mechanism: a truncated body reads as a signature failure)
  - The warning now fires only after **three CONSECUTIVE rejected requests** (`AUTH_FAIL_STREAK_TO_WARN`). Any success resets the streak AND re-arms the warning — credentials that worked and then stop working is a real event worth saying again (a unit re-provisioned by the cloud, a DHCP lease moved onto another Kumo unit). A busy or malformed reply neither extends nor clears the streak: it says nothing about the credentials, and clearing would let an adapter that alternates busy and auth hold a genuinely wrong credential below the threshold forever — only a success clears
  - At the default 15s poll a genuinely wrong credential still surfaces within a minute of startup; an isolated blip stays at debug, and the warning is latched per serial so the poller does not repeat it forever
  - Code: `local-api.ts:noteRequestOutcome / AUTH_FAIL_STREAK_TO_WARN`; tests in `test/local-http.test.ts` (two rejected requests warn nothing and the third warns; a success between rejections resets the count; credentials that stop working after working are warned about again)

- **2.3.0-ca.6** - A mode tap no longer takes a detour through the old mode (2026-08-19)
  - Fixed: tapping a mode in the Home app writes `Active` AND `TargetHeaterCoolerState` in one request, and `Active` resolves to the REMEMBERED mode — so a unit already on in heat got a redundant `heat` command before the `cool` the user actually asked for. Two LAN commands where one would do, and a visible detour through the old mode (observed live 2026-08-19)
  - The `Active` write is skipped only when nothing would change — and **NEVER for an off**: a redundant on is waste, but a swallowed off is a heat pump left running, and the cache it would be judged against can be stale or wrong. Regression tests in `test/dry-off-thermostat.test.ts` (a no-change write is not sent; an off always reaches the unit even when it already reads off; turning on a unit that is off still sends)
  - Code: `accessory.ts:setActive`

- **2.3.0-ca.5** - Canadian accounts via the v2 cloud, `localOnly`, and the first fixes from driving them (2026-08-19)
  - **`ca.1`–`ca.5` were rapid private builds**, each going from the working tree straight onto the installed Pi, so the build numbers mark deployments rather than tagged commits — and this entry collects the series. Two bodies of work: **the v2 cloud as a bootstrap** (Canadian accounts, and the secrets v3 stopped serving), then **`localOnly`** (run entirely on the LAN, with credentials you supply), which it builds on; plus the four fixes (`ca.2`–`ca.5`, at the end of this entry) that came from operating the result on real hardware
  - **Two new options, because the need has two independent axes.** `cloudRegion` (`"us"` default, or `"ca"`) is a fact about the ACCOUNT — which backend serves it. `localCredentialSource` (`"v3"` default, or `"v2"`) is about where the two per-device LAN secrets come from. The Canadian case fixes both at once, so it derives: `cloudRegion: "ca"` implies the v2 source and LAN control, and a Canadian configuration is `username`, `password` and that one line — no `localDevices`, no hand-copied secrets. The US case needs the other axis on its own, and it is the majority case today: v3 control works fine, v3 just no longer serves the secrets
  - **Canadian accounts can be used at all now.** `POST /v3/login` answers them **HTTP 500** — as against the 403 a genuinely wrong password gets, so the 500 is specific to an account the v3 backend knows and does not serve — and they live on `https://mesca-prod.kumocloud.com/login/v2`. One v2 sign-in supplies the unit list, each unit's room label, its real capability profile and both LAN secrets; control then runs over the LAN. **The v3 API is contacted on no path**: the same transport-level kill switch `localOnly` arms is armed for this region, which is the counter-intuitive part — the mode DOES contact a cloud (one POST, from a separate module) and must still leave v3 completely inert, or a command fallback, a site poller or a token refresh reaches an endpoint that answers 500 forever
  - **Since about 2026-07-31 the v3 cloud serves NOBODY the two secrets** ([pykumo #78](https://github.com/dlarrick/pykumo/issues/78)) — the `password` vanished from `adapter_update`, the `cryptoSerial` from `GET /devices/{serial}/status` — so `localControl: true` had become a no-op for everyone. `localCredentialSource: "v2"` restores it by reading both from the v2 login (`https://geo-c.kumocloud.com/login` for a US account), the same fallback Home Assistant's `mitsubishi_comfort` adopted in v0.5.2. The v2 reply is filtered to the serials v3 already discovered, so a unit present on only one backend is ignored rather than half-registered
  - **The host AND the path vary, so the option is a named region rather than a URL.** mesca answers `/login/v2`, geo-c answers `/login`. A free-form endpoint option was considered and rejected on three counts: an opaque host does not imply the protocol or the reply shape, it would be a credential-exfiltration footgun (point the plugin at any host and it posts the account credentials and collects the units' secrets), and it would have forced the `config.schema.json` layout assertion to be relaxed. `cloudRegion: "auto"` — try v3, fall back on the 500 — was rejected too: a 500 is also the signature of a transient outage, and it would post the credentials to a second host the user never named
  - **The REAL device profile replaces the synthetic one, and that fixes a heating floor.** `reportedProfile` carries the capability flags and **six** setpoint bounds, and the three floors genuinely differ on a unit with the extended temperature range: 10 °C heat against 16 °C cool on the mapped account (9 / 15 on another). A hand-declared `minSetPoint` is one number applied to all three modes, so such a unit was published with a **16 °C (60.8 °F) heating floor** — and hap-nodejs answers a client write below `minValue` with `-70410 INVALID_VALUE_IN_REQUEST` rather than clamping it, while `quantize()` snaps anything that slips past upward to 61 °F. The whole 50-61 °F band that freeze protection and vacation setback live in was unaskable. It is mapped per member now, per unit, with the synthetic profile kept as the fallback for `localOnly` and for a unit that has not reported a profile yet (`success: 0`, `firmwareVersion: "00.00.00"` in the wild)
  - **The Dry and Fan tiles stay opt-in here, unlike in `localOnly`.** That distinction is the reason `localOnly` was not simply extended: there `hasModeDry`/`hasModeVent` are hand-written per unit, so the declaration implies the tile; under v2 they are DISCOVERED, and both are true on ordinary hardware — so an implied tile would give every Canadian user two tiles nobody asked for, which is exactly the Home-app clutter the cloud path was made opt-in to avoid in 2.0.0. The single `localOnly` boolean was split into three named predicates (`v3Unavailable`, `inventoryFromV2`, and `localOnly` itself for "capabilities were declared"), because collapsing them is how "half a kill switch" happens
  - **Nothing from a v2 reply is ever logged, at any level, `debug` included.** One reply carries every unit's `password` and `cryptoSerial` in clear text, a session token, and the account holder's name, phone, email and every site's postal address. The parser reads only `root[2]` (the site tree) — plus, since `ca.3`, the single display-units boolean from `root[1]` (see that fix below) — and never even looks at the elements holding the personal data — unread data cannot leak — the type it returns structurally cannot hold a secret, so a leak would be a compile error rather than a review miss, and a failed sign-in logs a status code and a host name without reading the response body. The client deliberately does not go through `KumoAPI.makeAuthenticatedRequest`, whose debug lines print request bodies and error bodies verbatim (the login body is the account's username and password). `test/v2-log-redaction.test.ts` asserts all of it with `debug: true`, proving first that the sentinels really are in the payload so it cannot pass by finding nothing, and checking `accessory.context` too — that is written to disk in `accessories/cachedAccessories.<username>`. Its failure-path case scans EVERY recorded line at every level rather than the single error line: the likeliest way this rule ever breaks is one `log.debug(await response.text())` added while chasing a 401, and a check confined to the error line would not see it
  - **A security improvement over `localOnly`, not only a convenience.** The secrets live in memory for the life of the process: `config.json` is never rewritten, nothing is cached to disk, and a restart signs in again — which also means local control returns by itself if the vendor restores the v3 fields. One POST at startup, on a bounded retry with a **15-minute floor** (a sign-in reply is complete, so re-asking sooner cannot produce anything new), credentials in the body and never the query, `redirect: 'error'` so they cannot be re-sent to a host the user never named, and a **401/403 stops for good** — reported once, because repeating a rejected sign-in risks locking the account
  - **The existing seams are reused rather than reimplemented.** `admitLocalDevices` / `discoverDeviceIps` / `startLocalPolling` are untouched: a unit whose tree carries an `address` (or that is pinned in `localControlIps`, which wins) skips the LAN sweep entirely, and the rest go through the same token-matching /24 sweep. Registration is the same code path as `localOnly` — only the resolution above it differs — which keeps that loop's two silent ordering constraints in one place: credentials seeded BEFORE the handler is constructed, the profile emitted strictly AFTER it (the accessory subscribes in its own constructor, so emitting first drops the profile with no error, leaving default bounds, every mode offered and no Dry/Fan/Slats). MAC-based ARP resolution was evaluated and rejected: it saves a few seconds once per restart, needs an unreliable broadcast primer, needs three command formats across platforms (`arp` is absent from Raspberry Pi OS Lite, `ip` from macOS), and cannot replace the token probe anyway — and being L2 it would lose the L3 sweep's ability to reach a unit on another subnet
  - **`getZones` gained the kill-switch check it was only inheriting.** It is the one method in `kumo-api.ts` that builds its own `fetch(API_BASE_URL + ...)` instead of going through `makeAuthenticatedRequest`, so "no cloud in this mode" held only transitively — no token, no login, empty array. A bootstrap that seeds state onto the instance is exactly the kind of change that breaks that inheritance silently
  - **The validation matrix is two-way and, as first built, rejected six contradictions**, so a mistake was a startup error rather than a mode that is half on: an unrecognised value for either enum (a typo is **not** defaulted — `"can"` silently meaning `us` would point a Canadian account at the endpoint that answers it 500 forever), `ca` + an explicit `v3` source, `localOnly` + an explicit `v2` source, and either v2 route with `localControl: false`. Only an EXPLICIT value contradicts, which is what lets `ca` imply the rest without colliding with its own defaults — a premise the Homebridge UI turned out to break by writing schema defaults indistinguishably from choices, so `ca.8` downgraded the three of these six that have exactly one resolution (`ca` + `v3`, and both `localControl: false` variants) to warnings that absorb the value; only the enum typos and `localOnly` + `v2` remain startup errors. Two inert combinations are warned about instead of rejected. Both enums are normalised once in the constructor (`"CA"`, `" ca "`), the way `localOnly` already was

  - **The v3 "the cloud stopped serving the secrets" warnings are silent under a v2 credential source, because there they are false.** Both of them — the `adapter_update` password counter and the `cryptoSerial` one — fire on a v3 payload not carrying a secret, which is precisely what is EXPECTED once the secrets come from v2.   - **Every v3 payload dump is redacted by field name now, not by one destructured field.** The v2 module's logging rule only covers v2, and the v3 side is the side that prints whole vendor payloads: `RAW Zone JSON` (info level as soon as `debug: true`), the stream and adapter-update details, the request body, the error body — which is deliberately NOT debug-gated for a 400, because the validation message is the most useful line the plugin logs — and the accessory's `Zone adapter data`. A deny-list and not an allow-list on purpose: a field APPEARING is the hazard, and an allow-list would blank each newly-served diagnostic field until someone re-approved it, which is the same failure as having no logs.   - **New opt-in mode `localOnly`, for the two cases where the cloud cannot bootstrap local control.** It contacts the cloud on no path at all: no login, no site or zone fetch, no streaming, and no per-unit cloud fallback. - **2.2.0** - `node-fetch` is gone, the install is 9.4 MB smaller, and `engines.node` is plain `>=20` (August 2026)
  - **No functional change to either transport.** The cloud client moved to Node's built-in global `fetch`, and the LAN client moved to `node:http`. Both were verified to put the same bytes on the wire; what changed is what has to be installed to do it
  - **`node-fetch` was 9.4 MB of a 13 MB production tree, for a `fetch` the runtime already has.** Its subtree is six packages, and `web-streams-polyfill` alone is 8,936 KB — a polyfill for a stream type this plugin never touches. It also carried the runtime tree's only deprecated package, `node-domexception@1.0.0` ("Use your platform's native DOMException instead"), so a plain `npm install` printed a deprecation warning. Production is now **3,604 KB across 10 packages, down from 12,972 KB across 16**, and installs with no warnings. `socket.io-client` and its five transitive packages are the entire runtime dependency set
  - **`engines.node` is `>=20.0.0`, replacing `^20.19.0 || ^22.12.0 || >=24.0.0`.** Those patch-level floors were never about a language feature — they are the exact releases that first shipped `require(esm)`. node-fetch v3 is ESM-only, the plugin compiles to CommonJS, so `require()` of it threw `ERR_REQUIRE_ESM` on anything older and the floor had to name the backport points. Nothing in the runtime crosses the ESM boundary now: with `require(esm)` switched off, `node --no-experimental-require-module -e "require('./dist/platform.js')"` succeeds where it used to throw `ERR_REQUIRE_ESM`, and on 20.0.0 — which has no `require(esm)` at all — `dist/platform.js` loads and the full suite passes. The CI matrix runs that 20.0.0 now, so the declared floor is a tested one rather than an asserted one. Global `fetch` has been unflagged since 18.0 and printed no experimental warning on any 20.x checked (20.0.0, 20.18.1, 20.19.0), so 20 is a floor picked for what is tested, not for what is possible — `socket.io-client` is CommonJS and was never the blocker
  - **The LAN client went to `node:http`, deliberately *not* to global `fetch`.** Its two requests pass `agent: LOCAL_AGENT` — `keepAlive: false, maxSockets: 1` — and **undici, which is what global `fetch` is, ignores an `agent` silently rather than rejecting it**. That agent is load-bearing: these WiFi adapters have a tiny connection table and treat a parked socket as an occupied slot, which is why both reference implementations drop the connection after every exchange (pykumo `_drop_session()` with `pool_maxsize=1`; mitsubishi-comfort `disconnect()` in a `finally`). A swap to `fetch()` would have quietly put every LAN request back on a pooled keep-alive socket, and the symptom would have been intermittent local failures on real hardware, not a test failure
  - **The timeout is now two timers, and it takes both.** `http.request`'s `timeout` is a socket timeout: it covers a dead IP and an adapter that accepts then says nothing, and it destroys the socket instead of parking it — all of which the old `Promise.race` did not do. But Node arms it when the agent *assigns* a socket, so a request queued behind `maxSockets: 1` waits with no timer at all. Dropping the race for the socket timeout alone was measurably wrong: 8 requests to one origin at a 500 ms cap took **4,022 ms instead of 503 ms**, the cap having quietly become per-socket rather than per-call. `maxSockets` is per origin, so a /24 sweep never queued — 253 candidates are 253 origins, measured at 505 ms before and 508 ms after — but a rediscovery sweep probing an IP the poller is already talking to does. `signal: AbortSignal.timeout(...)`, armed at call time, restores the wall-clock bound; same case now settles in 506 ms
  - Durations are unchanged (6s for a poll or a command, 3.5s for a discovery probe), as is the `{ result, error }` contract and the deliberate absence of a status check — the adapter answers 200 to everything it parses, `_api_error` replies included. **One classification did change:** a socket destroyed mid-reply used to be swallowed by `res.json().catch(() => null)` and reported as `malformed`, which is not retried; it now surfaces as `transport`, which is. That is the better answer for a truncated read, but it is a real behaviour change and not the no-op the rest of this entry describes
  - **`test/local-http.test.ts` is new: 16 cases against a real `http.createServer`.** The LAN transport had no test at all — `local-api.test.ts` covers the pure token and mapping functions, `local-integration.test.ts` substitutes a fake client for the whole class — so the request line, the framing headers, the retry and the connection discipline were unasserted, and local control is vendor-blocked so there is no hardware to catch a mistake. The new tests pin the signed `PUT /api?m=<token>` against a token recomputed over the body actually sent, length framing rather than chunked, `Accept-Encoding: identity` (node-fetch advertised gzip and inflated the reply; nothing here can), each error kind end to end, the timeout and its single retry, and — the one that matters — that **two exchanges arrive on two different client ports**, which is what a reused socket would break. Each of those was confirmed to fail against a deliberately broken transport before being kept. Four more cases were added after mutation testing found the first sixteen blind to them: a per-call deadline under queue contention, a reply split across two writes, an adapter that dies mid-reply, and the `maxSockets: 1` half of the agent that the two-different-ports test does not reach. Each of the four was verified by reapplying its mutation and confirming exactly one failure. **273 tests total green**, on 20.0.0, 20.18.1 and 24.18.0
  - **`rimraf` is gone; the build wipes its output directory with Node itself.** `rimraf@3.0.2` is deprecated ("versions prior to v4 are no longer supported") and dragged in two more deprecated packages of its own — `glob@7.2.3`, and `inflight@1.0.6`, which is deprecated for leaking memory. It only ever deleted `dist/` and `dist-test/` ahead of `tsc`, and `node --eval "fs.rmSync('dist',{recursive:true,force:true})"` does that with nothing installed. Not `rm -rf`: npm runs scripts through `cmd.exe` on Windows. `node --eval` is the same command everywhere, `fs` is a global inside it — verified on 20.0.0, the `engines` floor, and on 22, 24 and 26 — and `force: true` makes a missing directory a no-op, so a clean checkout builds
  - **The `watch` script is gone with `nodemon`.** It had never worked. There is no `nodemon.json` and no `nodemonConfig`, so nodemon fell back to `main` and ran `node dist/index.js`, which registers the platform with Homebridge and exits; and its default watch list is `js,mjs,json`, so an edit under `src/` did not trigger it at all, and a trigger would have re-run node rather than `tsc`. A plugin is exercised by restarting Homebridge against a build, not by re-running its entry point
  - Together the two devDependency removals are 38 fewer packages installed, `fsevents` among them — the only remaining dependency with an install script. `q@1.1.2` is the one deprecation warning left in the *dev* tree and it is unrelated: it arrives through `homebridge` → `@homebridge/hap-nodejs` → `node-persist@0.0.12`, never through `rimraf`, and there is nothing to do about it here

  - **Faithful + safe push:** `applyMirror` normalizes `autoHeat`/`autoCool` → `auto`, clamps setpoints to the target's own range, skips modes the target can't do, and sends **one combined atomic command** (so the 1.7.2 trailing-setpoint race can't recur) via the local-first path. - **1.7.2** - Don't let an "AC off" scene revive the unit it's turning off (July 2026)
  - Fixed: an "AC off" HomeKit **scene** could leave a unit **running (in dry)** right after it fired. A scene is a saved snapshot of each thermostat's full state, so on every trigger it re-pushes `TargetHeatingCoolingState = OFF` *and* the captured setpoints — `TargetTemperature`, and for an AUTO unit the two AUTO band handles (`HeatingThresholdTemperature`/`CoolingThresholdTemperature`). HomeKit dispatches these concurrently in an arbitrary order. Given the LAN per-device mutex serializes in dispatch order, the unit reliably ends off

- **1.5.2** - Don't send a setpoint to a powered-off unit (June 2026)
  - Fixed: setting a TargetTemperature while a unit is off sent a bare `{ spHeat }` with no `operationMode`, which the Kumo v3 API rejects with `modeRequiredWhenDeviceOff` (HTTP 400). Every such attempt logged a cluster of red errors (`Request failed with status: 400` → `Send command failed` → `Failed to set target temperature`)

- **1.5.1** - Publish runtime-added features to HomeKit (June 2026)
  - Fixed: the fan-only switch (since 1.4.0), the dry switch (1.5.0), the humidity characteristic, and the filter indicator were all added to the accessory *after* it was published to the bridge (from async `profile_update` / first-reading callbacks) but never re-published — so they existed in memory and the HAP cache but never reached the Home app
  - Root cause: no `api.updatePlatformAccessories([accessory])` call after a runtime structural change. Centralized in `accessory.ts:publishStructureChange()`, called at every add/remove site (switches, humidity, filter)
  - `node:test` coverage extended (`test/switch-publish.test.js`) — asserts a re-publish happens on switch add/remove and on the first humidity reading; proven to fail against the pre-fix build
  - **Operational caveat:** publishing the service is necessary but not always sufficient. HomeKit controllers cache an accessory's *service list* and only re-read it when the bridge's configuration number (`c#`) increases. iOS will not surface services added to an already-paired accessory until its cache is cleared — a full **device reboot** (clears the `homed` cache) or removing/re-adding the child bridge. Force-quitting the Home app or restarting a Home hub is not enough.
  - Child bridge accessories persist to `accessories/cachedAccessories.<username-without-colons>` (e.g. `cachedAccessories.0EA3CB05C3A2`), NOT the main `cachedAccessories`
